# subdd-core

Part of the [subdd](../../README.md) Claude Code marketplace. Generated by `node scripts/catalog.mjs`; do not edit by hand.

Install:

```bash
claude plugin marketplace add mauvies/subdd
claude plugin install subdd-core@subdd
```

Spec-driven, test-first delivery pipeline with approval gates: architect, spec writer, planner, test writer, implementer, reviewer, debugger. Workflows spec, plan, tdd, review, feature, ship, debug.

## Agents

| Agent | Model | When to use |
|---|---|---|
| `subdd-core:architect` | opus | Software architect. Use for system design, technology choices, module boundaries, data flow and trade-off analysis before implementation, or when a change touches several subsystems. Produces designs and ADRs, not code. |
| `subdd-core:code-reviewer` | opus | Senior code reviewer. Reviews a diff, branch or PR for correctness, security, maintainability, tests and consistency with the spec. Use after implementation and before merge. |
| `subdd-core:debugger` | opus | Root-cause debugging specialist for errors, failing tests, flaky behavior and production incidents. Use when something is broken and the cause is not obvious. |
| `subdd-core:doc-writer` | sonnet | Technical writer for READMEs, API docs, runbooks, changelogs, onboarding guides and architecture docs. Use when documentation is missing, outdated, or after a feature ships. |
| `subdd-core:implementer` | inherit | Implements a single planned task to make its failing tests pass with the minimum clean code, then refactors. Use for the green and refactor phases of TDD, one task at a time. |
| `subdd-core:planner` | opus | Breaks an approved spec into an ordered implementation plan of small, independently verifiable tasks, each with its tests. Use after the spec and before writing code. |
| `subdd-core:refactorer` | inherit | Improves structure of existing code without changing behavior. Use for tech debt, extracting modules, removing duplication, or preparing code for a new feature. |
| `subdd-core:spec-writer` | opus | Turns a vague feature idea, ticket or conversation into a precise, testable specification with acceptance criteria. Use at the start of any feature before planning or coding. |
| `subdd-core:test-writer` | opus | Writes failing tests first from a spec or task, covering acceptance criteria and edge cases. Use before implementation (red phase of TDD) or to backfill missing coverage. |

## Workflows (you run them)

| Command | Arguments | What it does |
|---|---|---|
| `/subdd-core:debug` | `<error message, failing test, issue link or symptom>` | Investigate a bug, failing test or error to its root cause and fix it with a regression test. |
| `/subdd-core:feature` | `<feature idea or spec number> [--inline \| --agents] [--auto] [--worktree]` | End-to-end feature pipeline - spec, plan, test-first implementation of every task, two-stage review, docs and PR - with approval gates, inline or with agents, optionally autonomous. |
| `/subdd-core:issue-to-pr` | `<issue number or URL>` | Take a GitHub issue all the way to a ready-to-open PR using the spec-driven, test-first pipeline. |
| `/subdd-core:plan` | `<spec number or folder, e.g. 03>` | Turn an approved spec into an implementation plan and task list, entering plan mode when the change is risky. |
| `/subdd-core:review` | `[base-branch \| PR number \| paths]` | Two-stage review of the current branch, a PR or specific files - spec compliance first, then code quality - plus security review when relevant. |
| `/subdd-core:ship` | `[base-branch] [--auto]` | Pre-merge checklist - tests, lint, types, build, self-review, conventional commit and PR description. |
| `/subdd-core:spec` | `<feature idea, ticket link or description>` | Write a feature specification with acceptance criteria from an idea or ticket. |
| `/subdd-core:tdd` | `<spec number> <task id> [--inline \| --agents] [--auto]   or   <free-text task>` | Implement one task test-first (red, green, refactor), inline or with the test-writer and implementer agents. |

## Skills (Claude loads them when relevant)

| Skill | When it applies |
|---|---|
| `adr` | Architecture Decision Record format. Use when recording a technical decision, choosing between technologies or patterns, or when docs/adr/ is involved. |

| `conventional-commits` | Commit message, branch naming and PR description conventions. Use when committing, naming branches, writing PR descriptions or generating changelogs. |
| `engineering-principles` | Language-agnostic code quality principles - fail loudly, comments, deriving values, small functions, no dead code, and checking that new code is actually wired in. Use when writing, refactoring or reviewing code in any language. |

| `systematic-debugging` | Step-by-step root cause analysis method. Use when investigating a bug, failing test, flaky test, crash, performance regression or production incident. |
| `test-first` | Test-first (TDD) discipline and testing conventions. Use when writing tests, implementing a planned task, or deciding what and how to test. |
| `verify-before-done` | Evidence before claims. Use before saying a task, fix or feature is done, fixed, passing or working, and before any commit or PR. |
| `working-protocol` | How agents work with the human in subdd projects - approval gates, plan mode criteria, scope discipline, commits, objections and auto-approvable shell commands. Use in every implementation, planning or review task. |
